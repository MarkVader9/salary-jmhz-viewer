---
name: JMHZ Viewer is a compiled SolidJS bundle
description: The root JMHZ VIEWER app ships only as built artifacts; how to safely customize its runtime-rendered DOM.
---

The root JMHZ VIEWER (`/index.html`) loads a pre-built SolidJS app from `assets/viewer.runtime_*.js` (+ other hashed chunks in `assets/`, Monaco in `vendor/`), wired up by `manifest.js`. The SolidJS **source code is not in the repository** — only minified build output.

**Why:** The site was imported as a pre-built static bundle. UI like the upload drop-zone (`.drop-zone`), toolbars, etc. are created at runtime by the bundle, so they do not exist in the static `index.html` body.

**How to apply:** Never try to add ARIA/markup/behavior by editing the minified bundle or by editing static HTML that doesn't contain the element. Instead use **progressive enhancement**: a `MutationObserver` on `document.body` that finds the element once SolidJS renders it and applies attributes/handlers (guard with a `data-*` flag to run once). This is exactly how the marquee and drop-zone a11y enhancements in `index.html` work. CSS (e.g. `:focus-visible`) can target bundle-rendered classes directly.

**Injecting NEW elements into the drawer menu:** The hamburger drawer (`.drawer` → `.drawer-body`, with buttons like `.btn-jmhz-knihovna`) is also bundle-rendered and only exists in the DOM while open. To add a menu button, observe for `.drawer-body` and `appendChild` your button — guard by querying for your own class first to avoid duplicates, and remove any orphaned sibling (e.g. a `data-*`-tagged `<hr>`) before re-appending, since SolidJS may partially re-render the drawer body. Inline scripts/styles are CSP-allowed (`script-src 'unsafe-inline'`).

**Detecting "file loaded" vs "home/empty" state:** The toolbar (`.toolbar` → `.toolbar-left`/`-center`/`-right`) is sticky and **always present**, including on the home screen — do NOT assume toolbar presence means an XML file is loaded. The reliable signal is the upload drop-zone: `.drop-zone` exists **only** in the home/empty state. So `const fileLoaded = !document.querySelector('.drop-zone')`. For elements that should appear only while a file is loaded (e.g. a toolbar "Zavřít"/close button in `.toolbar-right`), have the MutationObserver `apply()` both add the element when `fileLoaded` and remove it when not, since the same observer fires across state transitions.

**Hard refresh as "close file / go home":** `location.reload(true)` after clearing Cache Storage + SW update (preserving `localStorage`) is the project's chosen mechanism to both refresh the bundle AND drop the in-memory loaded-XML state, returning to the home drop-zone. Reused for both the drawer "Oživit Prohlížeč" and toolbar "Zavřít" buttons.

**NEW XML formats CAN be added NATIVELY by surgically editing the runtime — the bundle is config-driven and pluggable. Do NOT build an overlay/parallel validator (user explicitly rejected that).** The compiled runtime renders WHATEVER `activeFormat` config it is given (Karty/Tabulka/Kontroly views are generic over the config), exactly like the built-in `REGZEC_CONFIG`/`JMHZ_CONFIG`. **Why it works:** classic (non-module) `<script src>` files share one top-level lexical scope, so a top-level `const FOO_CONFIG`/`FOO_SCHEMAS` declared in a sibling file loaded *before* `viewer.runtime.js` is visible to the runtime's bare-identifier references. **How to apply (the proven recipe, used for VZP HOZ + PPPZ):**
- **Three classic scripts**, loaded in `index.html`'s manifest loader chain (NOT bottom-of-body `<script>` tags — those load non-deterministically): `data/zp-xsd-data.js` (top-level `const HOZ_SCHEMAS`/`PPPZ_SCHEMAS`, filename→XSD-string maps; self-contained XSDs, no `<xsd:import>`) in the XSD phase; `assets/zp-formats.js` (`const HOZ_CONFIG`/`PPPZ_CONFIG`, also on `window`) right after `formats.js`; `assets/zp-kontroly.js` (`window.HOZKontroly`/`PPPZKontroly` with `runKontroly(xmlDoc, employees)` + `resetKontrolyIndex()`) in the kontroly phase. All phases finish before `viewer.runtime.js` loads.
- **Config shape** must mirror JMHZ_CONFIG elements-mode: `name, rootElement, ns, rowsContainer(|null), rowElement, schemasKey, mainSchema, kontrolyGlobal, sections[{id,label,_self?}], fields[{section,element,label}], _childOrder, _headerSpec, parseDocumentHeader, resolveSection, resolveSectionInstances(→null), readField, writeField, writeHeaderField, fieldAttrKey, fieldXpath, getRowLabel(fields), getRowInfo, headerFields:[]`. Runtime row-builder (`Kr`) keys `row.fields` as `"section/element"`; `getRowLabel` result is split on whitespace into `surname`/`firstName`. With `headerFields:[]` ALL sections (incl. `_self`) are processed.
- **~5 surgical runtime edits** (all driven by the active config so existing formats are untouched): (1) `detectFormat` — add `if (root.localName==='…') return X_CONFIG;` branches; (2) schema-lookup object literal `{DEFAULT_SCHEMAS,JMHZ_SCHEMAS,…}` — add the new `*_SCHEMAS`; (3) the "is-this-a-kontroly-capable-format" computed (was `Kn()||qn()`) — extend to test `p()?.rootElement` for the new roots, else the Kontroly button/guard exclude them; (4) the format-label computed — return the new short label by `p().rootElement`; (5) kontroly dispatch — `activeFormat?.kontrolyGlobal ? window[activeFormat.kontrolyGlobal] : (…)` and add the new `*Kontroly.resetKontrolyIndex()` calls in the reset block. `p()` returns the active config; `qn()` etc. already read `p().rootElement`.
- **Kontroly output contract** (matches the runtime consumer exactly): array of `{severity:'error'|'warning', controlId, empIndex, employeeName, sectionLabel, fieldLabel, fieldKey, headerKey, canNavigate, message}`; set `canNavigate:!!(emp.fields[fieldKey])`. `runKontroly` is called as `runKontroly(doc, [...rows], header, FIELDS, FIELDS_BY_SECTION, fieldRules)` — extra args optional.

**Shared validation primitives:** reuse `window.KontrolyUtils` (in `assets/kontroly-utils_*.js`) lazily *inside functions* (loads via the bundle; present at call-time, maybe not parse-time — keep local fallbacks): `validateRCModulo11` (`{valid,error}`, `error==='modulo'`=bad checksum), `validateIKMPSV`, `luhnCheck`, `validateCzPsc`, `findChildEl`, date helpers `parseDate/compareDates/addDays/todayDate/ageAt`, `evalRule`, `sanitizeEmptyXml`. NO 8-digit IČO validator exists — keep a local one.

**EDITING HAZARD — the minified runtime contains LITERAL TAB bytes inside template literals** (e.g. the CSV/clipboard delimiter array `a ||= [`,`,<TAB>,`|`,`;`,…]`). A literal tab is invisible in diffs and some editors/tools silently convert it to spaces on save, which **breaks delimiter detection for existing JMHZ/REGZEC import** — a regression with no syntax error. After ANY edit to `viewer.runtime_*.js`, `git diff` the whole file and confirm the ONLY changes are your intended ones; restore any tab→spaces drift (use a `\t` escape inside the backticks — functionally identical, but visible/robust).

**Verifying integration WITHOUT a browser:** the testing subagent can't upload a disk file. Instead run a Node smoke test: `@xmldom/xmldom` `DOMParser`, load the classic scripts via `vm` in one shared context (stub `window`, provide `getChildByLocalName`), replicate the runtime's `findRows`+row-builder (keys `section/element`), then call `window.XKontroly.runKontroly(doc, rows)`. Test both a valid sample (expect 0 findings) and a deliberately-invalid one (expect the warnings to fire) so you catch silent pass-through.
